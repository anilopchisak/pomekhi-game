# First-game lifecycle

The [target rules](../product/README.md) own gameplay intent. This document owns the shared seven-round lifecycle of First Game and Ordinary. Older design descriptions remain references for shared foundations and compatibility fixtures; the executable does not open older round-reset parties.

## Authority and data flow

[Lobby](../../src/server/lobby.ts) owns identity and command authorization. The [game](../../src/server/game.ts) owns phase, locked preparation, confirmed physical status, and the set of people waiting for a later deal. The [dealing owner](../../src/server/dealing.ts) randomizes balanced roles and excludes retained group cards from its eligible pool. Story source text is [server-only](../../src/server/first-game-content.ts). The editable catalog's harder flag is independent of historical level metadata.

The [search ledger](../../src/server/search.ts) has a round-local event log seeded with retained groups. Each group has an immutable original assignment identifier and frozen card; it can outlive the original member. New possessed members can report a permitted location during placement. The group carries that location until release. After recall, missing locations can be proposed and confirmed separately; they enter the next round without changing the current round search ledger. Search membership includes both new card recipients and retained members. The next round's rescue denominator counts live original assignments and its mission denominator counts newly dealt exorcists.

During active search, only a free exorcist's personal projection includes the member identities of releasable groups. The phone lists one option per group and sends one member identity for the selected group, preferring its original holder if still active. The search ledger resolves the identity and releases the entire group. It still accepts older reports with several selected identities. Each player's release history lists the members affected by their own accepted reports, including any groups released together by the matching card and location rule. The release dialog offers the existing dependency-aware undo or review on eligible reports. Infections remain in the reporting player's own infection dialog and can be undone independently when the rules permit.

The [round inbox](../../src/server/round-sync.ts) replays accepted events and retains decisions, dependencies and receipts. Phones send reports and acknowledge the journal using their personal inbox membership, including when they keep a card from an earlier round. A mission completed before recall can be reported during recall or checking, but always enters explicit review when received after recall. Reports delivered during a pause do not change the ledger. A gameplay report authored on pause is rejected. An organizer decision cannot override eligibility or causal undo. Physical status is recorded separately through the authenticated player's or organizer's command, and must match the current effective result. A network failure never creates a game status. A confirmed group can be kept in play without a connected phone. Unconfirmed free people can be confirmed at a later check.

## Transitions and presentation

The Mission Completed checkbox opens a confirmation for setting or clearing the mark. Confirming uses the existing mission command when connected or the local journal when disconnected. The projected completion flag controls the checkmark. The release dialog also offers dependency-aware undo of the latest mission report.

Preparation leads to reading, timed placement, timed exorcism, untimed recall, untimed checking, and the next deal or a terminal outcome. A player action cannot advance a timer; timer callbacks and organizer commands share the session queue. Early recall and a normal deadline recall share the free-only return path. Stop closes the pending result without scoring it and recalls everyone.

The session publishes a live recall cue with the committed game version after reconciling player presence. The cue keeps the transition timestamp for client freshness checks.

At finalization the game checks synchronization and physical return availability, carries unresolved groups, and commits the [ritual](../../src/server/ritual.ts) once. Confirmed total possession requires all remaining identities to be confirmed in groups. If some active players are disconnected at recall, the server starts a persisted return wait, normally 90 seconds. At expiry a confirmed online group, a still-disconnected expected player, no confirmed free returner and no unresolved release report permit a terminal no-return result. The timer and journal close commit together. A rescued medium at the base prevents that ending. A penalty has one legal source only when there is one maximum and it is not A. An explicit dismissal is recorded without moving a candle. Revealed prophecy state is independent of the current stack sizes.

The [protocol](../../src/shared/protocol.ts) has distinct organizer and personal projections. The organizer sees named initial roles and check statuses. A phone receives its own assignment and check status along with the target identities and action history authorized for its current role. Published candles are committed values. The shared laptop places the timer and settings in its toolbar, with a separate scroll region for reports and history. The organizer uses the base returns panel during recall and checking. Once the result is final, the next-round scene offers the new deal button and party history. The history also contains prophecy reports and penalty controls. A pending report is flagged in the history summary and blocks the new deal. The phone places its private card in the phase view. Dialog dismissal returns focus to the opener or to the refreshed target list when that opener is disabled. The timer is unknown without a fresh snapshot.

Review dialogs request a versioned server projection of either decision by replaying a detached inbox. They show the new provisional score and changed receipts. Confirmation carries the same game version; changes require a fresh projection. The penalty dialog uses the ritual's projected source, positions and remaining steps from the same calculation that moves the candle. The ritual view plays committed candle steps at 450 ms and shows a reveal for 500 ms. A forward step that empties a stack emits a 300 ms local smoke effect during playback. Reduced motion fades the extinguished candle without rising smoke. Skip, pause and lost connection drop presentation frames and display the committed snapshot.

## Preparation and violation reports

The game chooses a random story once at room creation and saves its identity and text in the existing checkpoint. The room projection carries the selected story. Saving the venue records the base, one or more permitted locations, and the selected categories. Preparation locks after the first deal, including if cancellation returns the room to the lobby.

The [deck history](../../src/server/deck-history.ts) records issued IDs outside the active room. Stories, the two ordinary prophecy slots, and mission pools by role and bank draw randomly from eligible IDs unseen in the current cycle. When the eligible set is exhausted, its cycle restarts and avoids the last draw if another option exists. IDs excluded by venue settings or the current deal keep their history. Assignments and retained groups still exclude duplicate cards in a deal, and prophecy selections exclude duplicates within their own batch. The final door is fixed. Drawing a card consumes it when the story, assignment or ritual is committed.

Room closure and new parties retain deck history. The session commits history and issued cards together, and a failed commit restores both from the same checkpoint. The private deck history is optional for older saves. On first restore the server seeds it with known cards and usage from the saved room. Reopening an issued story or deck does not draw it again. No history is sent to clients.

New rooms use Ordinary rules and the [server-only authored bank](../../src/server/authored-content.ts). The server checks card categories and admits two-location and contact requirements from the location count and the contact category. It excludes cards with any other venue requirement from new draws. The editable bank remains available to the organizer editor and to locked historical rooms that used it. Recovery discards the retired horror setting and venue feature flags, and new authored draws use base cards plus any enabled comedy missions. An unlocked checkpoint adopts the current setup and preserves any existing story.

New rooms enable indoor, contact, harder and comedy missions by default. The outdoor subset starts disabled. The comedy setting adds 24 possessed and 16 exorcist missions to the authored draw. The [server-only comedy source](../../src/server/comedy-cards.ts) supplies both the runtime and the offline catalog. Comedy missions have their own IDs and use the ordinary role pools and usage cycles. Venue setup saves the choice and locks it at the first deal. Existing rooms restore their saved choices. Issued comedy assignments restore from the saved text.

The [short card copy](../../src/server/short-card-copy.ts) is shared by the server and offline catalog. New personal assignments use one short sentence per answer, including any essential setup instruction. Each authored exorcist mission requires a scene that another participant sees or hears during the search. Saved assignments retain their issued text except for retired Dwelling missions, which are replaced consistently in dealing, search and offline replay when restored. Assignment IDs, journals and scores survive the replacement. New stories, prophecies and references use their short text in the existing game flow.

The host invitation and reading views reflect the committed phase. The toolbar room code opens the QR invitation in either view. The roster shows public deal status and has a confirmed redeal action next to its heading. The reading controls offer a manual start after a warning if some players are still reading or offline. Composition and pending replacement checks apply to both start paths. When a departure leaves fewer than five participants in the first deal, the organizer can cancel the deal from the reading controls and reopen admission with the same room code. The host can replace an assignment from the roster without exposing its private content.

Before the first round, a canceled deal can reopen admission if departures left fewer than five players. Replacements join the same room until the roster has five players. Preparation remains locked.

Phone violation reports carry the revealed prophecy slot and the player's account. The server exposes a personal reporting capability only when return to the base is confirmed: during checking, or during reading for a confirmed returner who received a new card. The same check guards the command. Authorized review accepts, rejects or dismisses the report without movement for a disputed pile. The decision and its candle change share the session commit. Duplicate commands do not move another candle.

## Storage and checks

The [disk store](../../src/server/session-store.ts) writes schema 8 to data/party-v8.json using the same single-writer lock and atomic commit. Without a v8 file it loads v7 or v6 and preserves the source file. The migration strips retired data from unsealed rounds. Recorded historical ritual movements and terminal outcomes are preserved. A locked v6 room keeps First Game rules. Only the catalog is imported from older saves. An I/O error reading the legacy file opens organizer recovery without writing a default bank. Retry imports the legacy catalog after access is restored. The [validator](../../src/server/session-format.ts) validates and replays the game and inbox before a checkpoint is accepted. Restore keeps a timed phase paused with its saved remainder, and preserves untimed recall and checking.

[Game tests](../../src/server/first-game.test.ts) cover balanced deals, carryover, sole return, loss, scoring, penalties and Pixso candle histories. [Transport and recovery tests](../../tests/integration/persistence.test.ts) use independent real clients and files for delayed review, identity recovery, and repeat finalization. Physical play, live network reachability, audibility, and real mobile devices require the separate [device checks](../testing/device-acceptance.md).
