# Lobby membership and recovery

> The executable uses the [first-game design](first-game.md). Below, older round, dealing, scoring and schema behavior applies to compatibility fixtures; shared foundation behavior still applies.

Status: implemented locally saved room with private-card reading and timed rounds. See [round design](rounds.md) for clock, pause and late-join behavior.

## Ownership and contract

[createLobby](../../src/server/lobby.ts) owns one active room, participant identities, revoked keys, organizer authorization and connection presence. App creates one instance per server behind a serialized session coordinator, injected into [Socket.IO](../../src/server/transport/socket.ts). Its interface is execute, disconnect, viewFor, subscribe and dispose; it imports no transport or bootstrap. Identifier and room-code generators can be injected for deterministic tests. The room also owns a game session composing dealing, and replay fingerprints; [dealing design](dealing.md) owns assignment/readiness semantics. No database or repository abstraction is required.

[The protocol](../../src/shared/protocol.ts) defines membership and dealing commands with acknowledged results and the lobby:state event. Runtime validation happens inside the lobby before changes. Anonymous connections receive server:ready only. Authorized organizers and joined players receive explicitly constructed projections; snapshots contain IDs, names, presence, room code, capacity and a monotonic revision, never resume keys or organizer credentials. Snapshots are detached copies. Private cards are added only to their authorized player projection by the [dealing owner](dealing.md).

Organizer authorization belongs to a connection and is checked on every control command. The process entry generates a random 12-character code for each launch, passes it into the server and intentionally prints it once in the local startup terminal. This bootstrap display is the sole credential-output exception; request/error diagnostics and the public readiness IPC contain no credentials. The panel stores its code in sessionStorage and authorizes again after each connection. A page URL alone grants no permissions. A new process invalidates the former code.

## Room and membership lifecycle

Creation returns the active room when one already exists. Capacity is 12, including offline participants; the shared laptop does not join automatically. Names use NFKC normalization, collapsed whitespace, a 1-24 Unicode-code-point limit and case-insensitive uniqueness. Control characters are rejected. There is no minimum membership requirement for an empty lobby.

Closing marks connected players as ended, disposes game timers and drops the room. The factory drains/checkpoints the coordinator while closing transports within the shutdown deadline. Organizer connections remain authorized and can create the next room. Room codes are six random unambiguous characters and are not reused within the retained save. Close, removal and leave commands identify the expected room so a stale command cannot affect a newer room.

The phone creates a cryptographically random 32-byte key and writes its room code, name, key and pending flag to localStorage before the first join. The server treats this key as a bearer credential. A repeated join with the same key returns the existing participant, even when its first acknowledgement was lost. Matching a name never recovers an identity. Once acknowledged, reconnect uses player:resume rather than creating membership. Automatic and manual retries for the same room retain the saved key: pending joins retry player:join, and acknowledged sessions retry player:resume. An uncertain response does not replace the credential.

Several tabs may attach to one participant. Presence stays online until its final connection disconnects; transport heartbeat detection can delay that update. Disconnection retains the slot. Leave and organizer removal delete membership, revoke its key for the room and notify every connected tab. A new manual join uses a new key. Closing a phone tab is not leaving the room. Losing the last authorized organizer panel pauses timed play; player departure, removal and withdrawal do not pause. Ordinary phone connection loss does not. New timed-phase arrivals wait for the next deal.

## Client composition and failures

App chooses HostPage with ?screen=host, otherwise PlayerPage. A ?room=CODE invitation pre-fills the player form. Root-query navigation works with the existing production HTML route and Vite proxy; no router is installed. Pages own login/join and action presentation. Client Shared owns the typed connection hook and the common visual shell used by both pages; page slices do not import each other. Page and Shared segment interfaces are index.js exports.

The connection hook creates and cleans up one Socket.IO connection per mounted page, including React StrictMode cleanup. Reconnect requests authorization or player recovery and receives a complete projection. A connection epoch rejects old acknowledgements, and a monotonic revision prevents older snapshots from replacing newer ones. Organizer controls have bounded acknowledgements and manual retries. Identity recovery and the durable player journal are automatically retried after reconnection. Read-only lobby:sync refreshes authorized state and clock without spending a command journal entry. An uncertain response asks the user to inspect the current room before repeating a control action.

The last authorized screen remains available during disconnection or uncertain recovery. Pages explicitly reset the connection projection after a definitive login/recovery rejection, clear the invalid credential and pending controls, and expose the login form without a reload. The offline model reads cached views and events only for its current credential scope; a revoked scope cannot keep a private screen visible or project actions onto a subsequent identity. Private-cache teardown has a stable callback and captures the cleared identity, so a later join's credential and cache survive delayed cleanup. Timeout, connection loss and storage unavailability retain the existing credential and screen.

Player recovery is scoped to the same browser and origin. A new process restores saved membership and accepts existing phone keys. The new organizer code is required on the laptop. Disabled or failed browser storage is reported before joining because an unpersisted key would strand a participant. The localStorage session is a browser credential. IndexedDB separately retains only the authorized private view and own journal for offline play. Disk saves and paused gameplay recovery are implemented by the [session coordinator](session-persistence.md).

The organizer pastes a public HTTPS origin into the panel; credentials, paths, queries and fragments are rejected. The panel constructs a code-bearing invitation and generates its QR locally using qrcode. This address is presentation state and never changes server/Tuna configuration. Clipboard failure retains a selectable URL. The organizer can join that invitation on a phone without sharing the organizer credential. Explicit LAN mode also permits private IPv4 HTTP origins; switching origin does not transfer browser sessions. See [offline participation](offline-play.md).

## Search recovery

The per-room game also supplies [PersonalPlay](search-actions.md): only the authorized participant receives its effective group card, capture/release state, mission eligibility and last undo identity. Reconnect restores that state without repeating physical actions. Public snapshots contain aggregate outcomes only after return finishes. Player play commands share the existing per-principal journal and validate round/game/play versions; result finalization requires organizer authorization.

## Verification

[Lobby rule tests](../../src/server/lobby.test.ts) cover authorization, normalization and capacity, idempotent joins, multiple tabs, revocation, stale room actions, isolated instances and credential-free detached projections. [Transport tests](../../tests/integration/lobby.test.ts) exercise independent real clients, seven participants, recovery, privacy, removal and replacement server state. [Recovery form tests](../../tests/tools/player-recovery.test.mjs) use React, DOM emulation, the real connection hook and lobby with controlled packet delivery to verify retained identity on uncertain responses, new organizer-code entry after restart and a fresh player join after offline removal without reloading. URL validation has focused tests. Browser evidence is recorded under ignored artifacts/lobby; native phones, QR camera scanning, Windows and mobile-carrier access require their actual environments.
