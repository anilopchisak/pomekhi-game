# Private cards and untimed reading

Status: implemented. [Game session](rounds.md) now owns timed phases; [search actions](search-actions.md) own effective roles, capture and team results.

## Owners and interfaces

[createDealing](../../src/server/dealing.ts) owns the current deal, assignments, readiness and replacement requests. It receives ID and uniform random-index generators. [The server bank](../../src/server/cards.ts) contains 60 original possessed cards (20 per level) and 30 missions (12/9/9 across levels 1/2/3), with optional infection conditions on possessed cards. The bank is not part of the shared protocol or client dependencies.

[Lobby](../../src/server/lobby.ts) owns authorization, membership, global projection revision and room lifetime. Each room has a game session composing dealing, plus its successful-request map. Lobby delegates card changes through game, which limits them to reading. New members receive a card during reading; timed-phase/break arrivals wait for the next deal. Explicit active-player departure revokes that assignment and pauses; ordinary phone disconnect only updates presence. Transport calls the serialized session coordinator; it does not select roles or read the bank.

The dealing interface provides deal, cancel, add, remove, change, publicState and personal. [The protocol](../../src/shared/protocol.ts) defines role/card unions, assignments, public dealing metadata and acknowledged commands. Public projections are detached and contain deal identity/version, the requested initial possessed count, composition validity and per-player assignment IDs/readiness/requests. Public assignment entries are sorted by player ID, independently of internal deal order, roles and history. Only an authorized player's view contains that player's role and card. Neither the organizer nor another player's view contains it. Actual role totals are not published, so adding one participant does not expose their role through a changing counter.

## Assignment lifecycle

New deals accept 4-12 members, including offline members, with 1 through floor(n/2) possessed. The laptop default is min(3, floor(n/2)). Fisher-Yates shuffles participant IDs, then a stable sort favors lower completed possessed-round history supplied privately by game. Equal histories retain random tie order; initial selection is uniform. Only normal return completion updates history; previews, reshuffles and aborted rounds do not.

A full shuffle uses the current roster and requested count, creates a fresh deal ID, increments its version, issues fresh assignment IDs and clears all readiness/requests. A preserved role still receives a different card. Each role draws from unused bank entries at the issued difficulty, excluding that player's previous card. If none remain, try the nearest simpler level, descending to 1. The level is supplied by game and persisted by dealing; replacement and reading newcomers use it too. This supports 11 unique exorcist cards even when only nine missions exist at the target level. Cards are unique within the active deal; bank entries can be reused across deals. Higher levels add linked actions or short sequences/memory, without extra physical risk or mandatory props. Missions remain optional and subordinate to rescues.

A late join during reading gets one role and unused card without changing existing IDs, readiness or the deal version. If fewer than two exorcists remain, add an exorcist; otherwise restore a missing possessed role. With both roles present, select uniformly between allowed roles when possessed are fewer than exorcists; otherwise add an exorcist. This keeps at least one spare card per role at the 12-player capacity. A resumed identity or retried join never draws another card.

Leave/removal deletes only that assignment and revokes membership through lobby. Remaining cards/readiness survive even when composition is temporarily invalid. The shared view offers a generic composition warning; it does not publish exact role totals. Cancel clears assignments and replacement requests, advances the deal version, and lets game restore the preceding lobby/break while retaining membership and party progress. Closing the room drops the dealing instance and its request cache.

## Individual actions and repeat delivery

Organizer-only commands are deal:create, deal:shuffle, deal:cancel and deal:replace. Replacement retains the target's role, takes an unused card, changes its assignment ID and clears only that target's readiness/request. Players can set their own card:ready and card:request. Requesting replacement clears readiness; withdrawing does not restore it. Readiness cannot be true while a replacement request is active. All-ready never advances a phase. Game rejects card changes, shuffle and cancel-deal outside reading, including during pause.

Every new command includes roomId, requestId, dealVersion and dealId; card changes also carry assignmentId. Runtime validation and actor authorization precede mutation and replay lookup. Successful commands are cached by room and stable principal (organizer capability or player ID), with SHA-256 fingerprints of only that command's validated fields in canonical order, independent of JSON property order. Unrelated fields are ignored and are never retained in the journal. Repeating the same request returns a current authorized projection without repeating its change. Reusing its ID for a different command or validated payload fails. No old private snapshot is cached or returned.

Each principal can retain at most 1024 successful request IDs, including successful no-op commands. Cached retries still work when the journal is full; fresh requests fail with REQUEST_LIMIT before any state mutation. Both pages describe the limit and ask the organizer to open a new room. Other principals retain their own budgets. Journals never evict entries within the room lifetime, so an old retry cannot execute a second time. Leave/removal releases that player's journal because the identity is revoked; closing the room releases every journal. With at most 12 members and one organizer journal, retained entries are bounded, and each fingerprint has a fixed size. This is a memory-retention limit, not a command rate limit.

The deal version changes on create/shuffle/cancel, independently of presence and readiness. Assignment IDs change on issuance/replacement. Different stale requests cannot act on another room, deal or newer card. Membership recovery remains idempotent through its pre-join key. These mechanisms prevent lost acknowledgements from causing a second shuffle/replacement or marking a new card read. The request map is included in durable room checkpoints.

## Browser behavior and recovery

Pages retain their existing public interfaces. Host-local DealControls selects the count for a new overall deal and confirms shuffle/cancel. The organizer list shows presence, readiness and requests, never private content; its projection carries opaque assignment IDs for targeted actions. Player-local PersonalCardPanel controls reveal state and sends only the current assignment identity with actions. Shared API supplies command identities and the existing typed connection.

Cards start closed. Reveal/hide is local presentation state keyed to the assignment ID, independent of server readiness. New cards and refresh start closed; brief reconnect retains the screen; the same role/card/readiness returns from the server. Tabs share readiness and requests but each controls its own reveal state. The credential session stays in localStorage. IndexedDB stores only the authorized personal view and own queue for [offline play](offline-play.md); it never stores the bank. Phones remain silent and use readable CSS without effects over text.

Card and organizer commands have acknowledgement deadlines and manual retry. Only stable gameplay journal events are automatically resent after identity recovery. A visible manual retry retains the original request payload/ID. The connection epoch rejects older acknowledgements and the global projection revision prevents older snapshots from overwriting current views. A full restart restores cards and readiness without consulting the bank; versions advance to reject unsent stale intents. See [persistence](session-persistence.md).

## File exposure and verification

Production HTTP serves only dist/client. Development file serving allows client, neutral shared and node_modules directories, keeping project/tool snapshots outside its filesystem roots. Vite's fs.deny also extends the pinned defaults with server source, compiled-server and private data patterns. Both transformed and raw requests are blocked, while neutral shared contracts remain available. The default environment/key/Git/npm configuration restrictions remain present. No bank is stored in a public directory or logged in diagnostics.

[Rule tests](../../src/server/dealing.test.ts) exercise composition, uniqueness, replacements, shuffle and late membership with deterministic generators. [Journal tests](../../src/server/lobby-requests.test.ts) exercise bounded retention, ignored unrelated fields, retries at capacity, independent principals, reconnect and room replacement through the real lobby interface. [Real transport tests](../../tests/integration/dealing.test.ts) verify personal projections, offline cards, recovery, repeated/stale commands, ignored unrelated fields, capability restrictions and bank exclusion from built assets/HTTP. [Vite tests](../../tests/integration/private-files.test.ts) reproduce the previous exposure and assert 403 for source/build requests, with and without raw. [DOM tests](../../tests/tools/cards-ui.test.mjs) use real React, connection and lobby with controlled delivery for concealment, readiness, replacement, lost acknowledgements and the request-limit message.

Browser/Tuna evidence belongs under ignored artifacts/dealing. macOS Chromium/WebKit viewports are separate from native Windows and physical iOS/Android acceptance.
